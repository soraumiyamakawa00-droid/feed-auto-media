# 想定Q&A ／ 権利・リスク整理

## A. 先方から必ず聞かれること

### Q0. 「そんなにいい話なら、なぜ御社がやらないんですか？」
**必ず聞かれます。ここで詰まると全部終わります。一字一句、固めておいてください。**

**A.** **IPがないからです。**
この構想はIPがなければ成立しません。
ゼロから作ったキャラクターでは「初めて会った日からの積み重ね」しか生まれません。
御社のIPには、**ユーザーが子どもの頃から積み上げてきた27年分の関係**が既にあります。
これは後からいくら開発しても作れない部分です。

加えて、仮に私どもが御社のIPをお借りして開発・運営したとしても、
御社に残るのはロイヤリティだけになります。
開発ノウハウも、ユーザーとの直接の関係も、行動データも当社に溜まる。
**それは御社にとって損な取引です。**

だから、エンジンと作り方をお売りして、事業は御社のものにしていただく形をご提案しています。

---

### Q1. 「実績はありますか？」
**A.** 自社オリジナルキャラクター「ロウ」で実装した参考機があります。
まずそれをご覧ください。【要確認: ロウの実装状況に合わせて確定】

なお本提案は運営代行ではなく、御社が開発・販売される前提です。
そのため求められるのは運営実績ではなく**「実装できることの証明」**だと考えており、
参考機はまさにそのためにご用意しています。

---
### Q2. 「キャラクターに変なことを言わせませんか？」
**A.** 4層で防ぎます。
1. 挨拶・励ましなど頻出シーンは**監修済みの固定セリフ**を使い、生成AIには回しません
2. 生成する場合も、前後に二段のフィルタ（NG語・設定違反・センシティブ領域）を通します
3. 全応答をログ保存し、問題があれば即時ロールバックします
4. **御社にはいつでもサービスを停止させる権利**を契約に明記します

### Q3. 「学習データにうちのIPを使いますか？」
**A.** **使いません。** モデルの追加学習は行わず、監修済みの設定データを
実行時に参照する方式（プロンプト＋検索）を採ります。
御社のデータがモデルの重みに取り込まれることはありません。

### Q4. 「声はどうしますか？」
**A.** 3つの選択肢があり、御社にお選びいただきます。
| 案 | 内容 | 論点 |
|---|---|---|
| ① 既存音源の利用 | 収録済みボイスを再生 | 声優さんとの契約で二次利用が可能か |
| ② 新規収録 | 本アプリ用に収録 | 予算と収録量。追加ボイスのたびに収録 |
| ③ 合成音声 | 声優さんの同意を得たうえで音声合成 | 同意取得が必須。反発リスクあり |

**初期は ① または ② を推奨**します。③ は事業が軌道に乗ってから改めて議論すべき論点です。

### Q5. 「ユーザーの画面を見るんですか？」
**A.** **見ません。** 画面のキャプチャ・内容解析は一切行いません。
取得するのは「アクティブなアプリの種別」「入力の有無」程度で、すべてオプトインです。
拒否されても基本機能は動作します。

### Q6. 「Desktop Mate と何が違うんですか？」
**A.** レイヤーが違います。
Desktop Mate は「キャラクターがそこに**いる**」ことを提供するプラットフォームです。
本提案は「キャラクターがユーザーの**行動を変える**」ことを提供します。
そして進化の条件が**ユーザーの実生活の達成**である点は、既存のどのデスクトップマスコットにも
既存のどの育成ゲームにも存在しません。

### Q7. 「うちで内製できるのでは？」
**A.** **ぜひ内製してください。それが本日のご提案です。**

見た目・モーション・世界観は御社が作れます。当然です。
お持ちしたのは、内製されるにあたって**ゼロから作ると時間がかかる2つ**です。

1. **中身** — 「人の行動を実際に変える」部分（Addness）。
   これはキャラクター制作とは全く別の技術領域で、ゼロから作ると数年かかります
2. **作り方** — 監修の往復を即日で回す開発手法（Claude Code）

御社に開発リソースが今すぐ確保できない場合は、
当社が初期開発を担当して工程ごとにお渡しする **B案（内製化支援型）** もご用意しています。

---
### Q8. 「AIへのファンの反発が怖い」
**A.** 最大の懸念だと理解しています。だからこそ**公式が先に、監修付きで出す**ことに意味があります。
非公式のAI二次創作は既に存在し、コントロールできません。
公式が「ここまでは公式、ここからは違う」という基準を示すこと自体が、IPの防衛になります。
また、学習データの扱い・監修体制を公開することで、誠実さを前面に出す発信設計をご提案します。

### Q9. 「収益の分配は？」
**A.** **A案・B案では、売上は全額御社のものです。**
当社の対価はエンジンのライセンス料と技術支援フィーで、売上からの分配は受けません。

当社が開発を請け負い、かつ初期投資を抑えたいというご要望がある場合のみ、
レベニューシェアを含む **C案（共同開発型）** をご用意しています。
ただし御社の資産が最大化されるのは A案です。

### Q10. 「いつ黒字になりますか？」
**A.** Phase 3 の一般公開（開始から約16ヶ月後）から収益が立ち始める想定です。
Phase 0〜2 は投資期間となります。

ただし Phase 0 は**当社負担での実施も可能**で、
そこで御社にご負担いただくのは会議3回分のお時間だけです。
**投資判断そのものを、実機を見てからに後ろ倒しできる**設計にしています。

### Q11. 「エンジンだけ買えばいいのでは？」
**A.** **その通りです。それが本日のご提案です。**
Addness はOEM供給が可能で、御社のアプリの中で動きます。
そのうえで、立ち上がりだけは伴走させてください、というのが Phase 0 のお願いです。

### Q12. 「Addness に依存することになりませんか？」
**A.** 依存を避ける設計をご提案します。
連携部分はインターフェースを切って抽象化し、
行動ログと成長パラメータの定義は**御社側に置きます**。
契約にはソースコードのエスクロー、および
サービス終了時の移行猶予期間を盛り込むことが可能です【要確認: 自社として対応可能か】。

## B. 権利まわりの整理（契約交渉前に自社で詰めること）

| 論点 | 確認事項 | 想定される落としどころ |
|---|---|---|
| **IP利用許諾** | 対象キャラ、期間、地域、媒体（PCアプリ）、独占か非独占か | 非独占・日本先行・2年更新 |
| **原作権の所在** | デジモンは企画=ウィズ／発売=バンダイ。権利が分散 | 両社の許諾が必要な前提で動く |
| **映像アセット** | アニメ版の素材を使うなら東映アニメーションの許諾も別途 | 初期は使わず、3Dモデルは新規制作 |
| **声優** | 既存音源の二次利用可否、新規収録の条件、合成音声の同意 | 初期は ①既存音源 or ②新規収録 |
| **音楽** | BGM・SEの利用権 | 新規制作が安全 |
| **生成物の帰属** | AIが生成したセリフ・挙動の権利 | 御社帰属とするのが通りやすい |
| **学習利用の禁止** | 御社資料をモデル学習に使わない旨 | 契約に明記 |
| **停止権** | 御社が一方的にサービスを停止できる条件 | 契約に明記（先方の安心材料になる） |
| **監修義務** | 何を、どの頻度で、誰が承認するか | 週次差分レビュー＋ステージング承認 |
| **データの帰属** | 利用ログ・行動データの所有者 | 共有。個人特定情報は当社が保持しない |
| **独占交渉期間** | 提案内容を他社に持ち込まない期間 | 3〜6ヶ月 |

> **注意**: 上記は交渉の論点整理であり、法的助言ではありません。
> 実際の契約締結前に、必ず弁護士のレビューを受けてください。

## C. 事業リスクと打ち手（自社視点）

| リスク | 兆候 | 打ち手 |
|---|---|---|
| 監修で開発が止まる | レビュー待ちが2週間超 | 承認SLAを契約に入れる。ステージング常時公開 |
| 権利処理が半年かかる | 法務レビューが長期化 | Phase 0 は「社内検証目的・非公開」で権利処理を最小化 |
| Addness への依存 | 仕様変更・障害 | 連携層を抽象化。行動支援ロジックの一部は自社に保持 |
| 常駐アプリの性能問題 | CPU/メモリ苦情 | Phase 0 で計測。軽量モードを標準搭載 |
| 「うるさい」離脱 | 通知オフ率が高い | 介入頻度を学習で調整。黙る判断を実装 |
| 競合の先行 | 大手が同種機能を発表 | スピード。Phase 0 を最速で回す |
| 相手企業の組織変更 | 窓口が異動 | 窓口を複数持つ。議事録を残す |
| **「中身も自分たちで作る」と言われる** | エンジン採用を見送られる | Addness の"行動を変える"部分の再現難度を具体的に説明。B案で入口を作る |
| **エンジン供給のみで単価が伸びない** | 受注額が小さい | Phase 0〜1 の開発支援フィーと、長期のライセンス収入で設計する |
