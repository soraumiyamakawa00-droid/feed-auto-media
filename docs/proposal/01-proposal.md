## 1. なぜ今、なぜ御社なのか

### 1-1. 「デバイスの中で生き物を育てる」の原点

1996年にウィズが企画・原案し、1997年6月26日にバンダイから発売された『デジタルモンスター』は、
**「小さな画面の中に、自分だけの存在が住んでいて、世話をすると育つ」**という体験を発明しました。

29年後のいま、同じ体験を作る条件が揃っています。

- 画面は携帯液晶から **常時起動のPCデスクトップ** になった
- 「世話をする」は **ボタン入力から自然言語の会話** になった
- 「育つ」は **プログラムされた進化条件から、ユーザーの実生活の記録** で駆動できる

つまり、**あの原体験を、現代の技術でやり直せる唯一のタイミング**です。
そしてそれを最もやるべきなのは、あの体験を発明した御社だと考えています。

### 1-2. IPホルダー側の課題認識

| 課題 | 現状 | 本提案での解 |
|---|---|---|
| 放送・配信の端境期にIPが沈黙する | 新作の間はグッズと過去作視聴のみ | 毎日起動するPC常駐で接触が途切れない |
| ファンの実態が数字で見えない | 売上とSNSの反応が主な指標 | 誰が・どのキャラを・どれだけ使うかが一次データで取れる |
| 若年層のTV離れ | 接点が受動的メディアに依存 | 能動的に「使う」接点を持てる |
| 生成AIとIPの距離感 | 無断学習・二次創作への不安 | **公式が監修したAIキャラ**を先に出すことが最大の防御になる |

最後の1行が、本提案のいちばん強い主張です。
**公式が出さなければ、非公式が出ます。**

## 2. 提供する体験

### 2-1. ユーザーから見た一日

```
07:30  PC起動。デスクトップの隅で相棒が伸びをする。
       「おはよう。今日は15時に打ち合わせだね。その前に例の資料、
        30分だけ先に片付けておかない？」

10:00  作業中。ウィンドウの縁に腰かけてこちらを見ている。
       集中が切れてSNSを開くと、そっと画面の端に寄ってくる。

15:00  会議終了。「おつかれ。さっきの宿題、3つに割っておいたよ」
       → Addness 側にタスクが3件、自動で分解されて積まれている。

23:00  「今日は4つ終わったね。今週いちばんだ」
       → 達成ログが相棒の成長値に加算される。

(数週間後) 小さかった相棒が、ひとつ上の姿に進化する。
```

**ポイント: 「進化」の条件が、ゲーム内行動ではなく "ユーザーの実生活の達成" である。**
これは既存のデスクトップマスコットにも、既存の育成ゲームにも存在しない体験です。

### 2-2. 3つの機能の柱

#### ① 住む（Presence）
- デスクトップ常駐。ウィンドウに座る・登る・カーソルを追う
- 3Dモデル（VRM）または2Dライブ表現に対応
- 時間帯・天気・PCの状態に反応する待機モーション

#### ② 動かす（Action / ← Addness）
- 目標を会話で受け取り、中期・短期タスクに自動分解（Goal Breakdown）【要確認: 正式機能名】
- ToDo管理、リマインド、進捗の振り返り
- カレンダー・チャットツール連携【要確認: 現行の対応範囲】

#### ③ 育つ（Growth）
- 継続日数・達成数・対話量を成長パラメータに変換
- 一定条件で「進化」＝見た目とボイスと性格が変わる
- 分岐進化により、ユーザーごとに違う相棒になる

## 3. なぜ Addness と Claude Code なのか

### 3-1. Addness（AI行動支援OS）

アドネス株式会社が2025年12月21日に正式リリースしたAI行動支援OS。
「話すだけでやるべきことが明確になり、気づけば進んでいる」状態を目指すプロダクトで、
目標設定・計画設計・実行管理を対話で支援します。2026年3月時点でユーザー数5,000名を突破。
【要確認: 最新のユーザー数・法人導入社数に差し替え】

本提案での役割は **「キャラクターの中身」**です。
キャラクターAIを一から作ると、雑談はできても生活は変えられません。
Addness は既に「行動を変える」部分が動いている。
**ガワ（キャラクター）を御社が、中身（行動OS）を当社が持ち寄る構造**が、最短距離です。

### 3-2. Claude Code

Anthropic の開発エージェント。当社は開発工程の実装をこれで回しています。

- **プロトタイプまでの速度**: Phase 0 の動くPoCを **2〜3週間** で提示可能
- **監修サイクルの速さ**: 「この口調は違う」への修正を、その日のうちに反映して再提示
- **少人数で回る**: 大規模な開発チームを抱えずに継続改善できる

IP案件で最も摩耗するのは「監修と手戻り」です。
ここを速くできることが、実質的な提案価値です。

### 3-3. 御社が持ち寄るもの

- キャラクターIPと世界観
- 口調・性格・NG表現のレギュレーション
- 監修（キャラクターが壊れていないかの最終判断）
- ボイス・BGM等の既存アセット（利用範囲は別途協議）

## 4. キャラクターを壊さないための設計

IPホルダーが生成AIに対して抱く最大の懸念は
**「うちのキャラクターに、言わせてはいけないことを言わせるのでは」**です。
本提案ではここを技術課題として正面から設計します。

| 層 | 対策 |
|---|---|
| 人格定義 | 口調辞書・一人称・語尾・禁止表現を構造化データで管理。監修済みのものだけを本番投入 |
| 応答制御 | 生成の前後に二段のフィルタ。NG語・作品設定違反・時事/政治/宗教/医療等の領域を遮断 |
| 定型優先 | 挨拶・励まし・進化演出など頻出シーンは**監修済み固定セリフ**を優先し、生成は補完に回す |
| 監修フロー | 変更はすべて差分で提出。御社の承認前は本番に出ない（ステージング環境で確認） |
| ログ | 全応答を保存し、いつでも遡って検証できる。問題発生時は即時ロールバック |
| 段階公開 | クローズドβ → 限定公開 → 一般公開。各段階で御社の停止権を明記 |

**「AIに全部しゃべらせる」提案ではありません。
「監修済みの表現を、AIが適切なタイミングで届ける」提案です。**

## 5. 事業性

### 5-1. 収益モデル（3案）

| 案 | 構造 | 御社のリスク | 御社の上振れ |
|---|---|---|---|
| **A. レベニューシェア型** | 当社が開発・運営費を負担。売上をレシェア | 小（費用負担なし） | 中 |
| **B. ライセンス＋MG型** | 当社がミニマムギャランティを支払い、ライセンスを受ける | 極小（先に収入） | 小〜中 |
| **C. 共同事業型** | 開発費を折半、権利と収益も折半 | 中 | 大 |

**初回は A を推奨**します。御社の持ち出しゼロで始められ、Phase 1 の数字を見てから B/C に組み替えられます。

### 5-2. 収益の入口

1. **アプリ内課金**: 追加キャラクター、衣装、ボイス、進化分岐の解放
2. **サブスクリプション**: 高度な行動支援機能、複数キャラ同時常駐
3. **法人向け**: 企業の社内利用（従業員の目標管理をキャラクターが支援）
4. **タイアップ**: 期間限定コラボキャラ、企業スポンサー枠
5. **既存事業への送客**: 新作告知、配信サービス、EC、イベントへの導線

### 5-4. 金銭以外のリターン

- **一次データ**: 起動時間、利用継続率、人気キャラ、人気ボイス、進化分岐の選択率
