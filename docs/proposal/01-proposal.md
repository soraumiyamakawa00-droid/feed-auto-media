## 0. 本提案の主旨

**「うちにIPを貸してください」という提案ではありません。**

**御社が開発し、御社が売る。**
私どもは、そのために足りない「中身」と「作り方」をお持ちしました。

- 開発するのは御社です
- 売るのも御社です
- 収益もファンデータも、すべて御社に残ります
- 私どもはエンジン（Addness）と開発手法（Claude Code）を提供する立場です

なぜこの形にしたのか。理由は第5章に書きました。

## 1. 1997年、御社は早すぎた

1996年にウィズが企画・原案し、1997年6月26日にバンダイから発売された『デジタルモンスター』。
あの製品が提示していた構想を、いまの言葉で書き直すとこうなります。

> **デバイスの中に、自分だけの存在が住んでいる。**
> **世話をすると育ち、世話の仕方で姿が変わる。**
> **放っておくと弱る。だから毎日気にかけてしまう。**
> **そして、その存在は他の人の存在とつながれる。**

これは29年前の玩具の仕様ではありません。
**2026年のAIエージェントが目指している姿そのもの**です。

そして1999年からの『デジモンアドベンチャー』が広めた
**「パートナーデジモン」**という概念 ──
一人にひとり、自分だけの相棒がいて、一緒に成長する ──
これも、いま世界中の企業が「AIアシスタント」の名前で追いかけているものです。

**御社は、27年前に答えを出していた。**
足りなかったのは、それを実装する技術だけでした。

## 3. 作るもの：PCの中に住むパートナー

### 3-1. ユーザーの一日

```
07:30  PC起動。デスクトップの隅でパートナーが伸びをする。
       「おはよう。今日は15時に打ち合わせだね。
        その前に例の資料、30分だけ先に片付けておかない？」

10:00  作業中。ウィンドウの縁に腰かけてこちらを見ている。
       集中が切れてSNSを開くと、そっと画面の端に寄ってくる。

15:00  会議終了。「おつかれ。さっきの宿題、3つに割っておいたよ」
       → タスクが3件、自動で分解されて積まれている。

23:00  「今日は4つ終わったね。今週いちばんだ」
       → 達成ログが成長値に加算される。

(数週間後) 小さかったパートナーが、ひとつ上の姿に進化する。
```

### 3-2. 核心は「進化条件」

**進化の条件は、ゲーム内の操作ではありません。ユーザーの実生活での達成です。**

```
[実生活の達成]     →  [成長パラメータ]  →  [進化]
  タスクを完了した        活力
  毎日起動した            絆
  早起きが続いた          規律          → 分岐条件を満たすと
  振り返りをした          内省             姿・声・性格が変化
```

- 課金では進化を買えません。生活を変えないと育ちません
- 分岐進化により、同じ初期形態でも育ち方が人ごとに変わります
- **1997年の育成ロジックを、現実世界に接続しただけ**です。発明ではなく、完成です

### 3-3. 既存のデスクトップマスコットとの違い

市場には Desktop Mate をはじめ、キャラクターがデスクトップに常駐するアプリが既にあります。
しかしそれらは **「いる」** を提供するものです。

本構想は **「育つ」「変える」** を提供します。
この差は機能の差ではなく、**ユーザーがアンインストールできなくなるかどうか**の差です。

## 5. 足りない「作り方」：Claude Code と、その提供理由

### 5-1. IP案件で最も摩耗するのは、監修の往復です

キャラクターアプリの開発で開発費を食うのは、機能の実装ではありません。
**「この口調は違う」「この動きはこの子じゃない」への修正を、何往復もすること**です。
通常これは1往復に1〜2週間かかります。

私どもは開発実装に Claude Code（Anthropicの開発エージェント）を使っており、
**監修のご指摘を、その日のうちに直して再提示できます。**

- 動くプロトタイプまで **2〜3週間**
- 修正の反映は **即日〜翌日**
- 大規模チームを抱えずに継続改善できる

これは開発コストの話ではなく、**御社の監修担当者の消耗を減らす**話です。

### 5-2. なぜ「御社で開発して売る」形をご提案するのか

ここが本提案の核心なので、正直に書きます。

**理由1: 私どもにはIPがありません。**
この構想はIPがなければ成立しません。ゼロから作ったキャラクターでは、
「初めて会った日からの積み重ね」しか生まれません。
御社のIPには、**ユーザーが子どもの頃から積み上げてきた27年分の関係**が既にあります。
これは後から作れません。

**理由2: 御社にとって「貸す」形は損です。**
仮に私どもがライセンスをお借りして開発・運営した場合、御社に残るのはロイヤリティだけです。
開発ノウハウも、ユーザーとの直接の関係も、行動データも、当社側に溜まります。
**御社が作れば、全部が御社の資産になります。**

**理由3: IPの安全は、内製がいちばん確実です。**
「キャラクターを壊されるのでは」という懸念に対する最も確実な答えは、
外部に厳しい契約を課すことではなく、**御社自身が手綱を握ること**です。

だから、こう申し上げます。
**エンジンと作り方をお売りします。事業は御社のものにしてください。**

## 6. 座組み（3案）

| 案 | 構造 | 開発 | 収益 | 当社の対価 |
|---|---|---|---|---|
| **A. エンジン供給型**（推奨） | 御社が開発・運営。当社は Addness をOEM供給＋技術支援 | 御社 | **全額御社** | エンジンライセンス料＋支援フィー |
| **B. 内製化支援型** | 当社が初期開発を担当し、工程ごとに御社へ移管 | 当社→御社 | **全額御社** | 開発費＋移管支援フィー |
| **C. 共同開発型** | 当社が開発を請け負い、御社が販売・運営 | 当社 | 御社（一部レシェア） | 開発費＋レベニューシェア |

**初回は A を推奨します。** 御社の資産が最大化され、IPも社外に出ません。
御社に開発リソースがすぐ確保できない場合は B で始め、段階的に内製へ寄せる形が現実的です。

## 7. キャラクターを壊さないための設計

御社が内製される場合でも、この設計思想はそのままお渡しします。

| 層 | 対策 |
|---|---|
| 人格定義 | 口調辞書・一人称・語尾・呼称・禁止表現を構造化データで管理。監修済みのものだけ本番へ |
| 応答制御 | 生成の前後に二段フィルタ。NG語・設定違反・時事/政治/宗教/医療等を遮断 |
| 定型優先 | 挨拶・励まし・進化演出など頻出シーンは**監修済み固定セリフ**を優先。生成は補完に回す |
| ログ | 全応答を保存。問題発生時は即時ロールバック |
| 段階公開 | クローズドβ → 限定公開 → 一般公開。各段階で停止判断を置く |

**「AIに全部しゃべらせる」構想ではありません。**
**「監修済みの表現を、AIが適切なタイミングで届ける」構想です。**

また、**御社の設定資料をAIモデルの学習には使いません。**
実行時に参照する方式を採り、モデルの重みに御社のIPが取り込まれることはありません。
